## Why this week matters

For seven weeks you have been writing C: declaring every type, ending every line with a semicolon, counting to the `\0`, asking for memory and giving it back. It was hard on purpose. You now know what a variable *is*, what a string *is*, what a function call *costs*. This week you get your reward. **Python** is a language built by people who had done all of that and wanted to stop. Every idea you learned stays; most of the ceremony goes.

Python is also, at this moment in history, the most useful language you can know. It is the language of AI: every model you have heard of is trained from Python. It is the language of data, of automation, of science, of the scripts that keep companies running. It is also the language of the second half of this course: AI next, then SQL, then the web.

Here is the one sentence to keep: **Python is C with the hard parts hidden**. Hidden, not gone. When Python is fast, it is because C is doing the work underneath. When Python is slow, you now know why, and you are one of the few people in the room who can do something about it.

## Compiled versus interpreted

Think of a book and a conversation. A **compiler** is a translator who takes your whole book, translates it once, and hands you a finished copy in the machine's language. That is `make hello`: slow to prepare, fast to read, and if there is a mistake on page 200, the translator refuses to deliver anything at all. An **interpreter** is the person standing next to you at a meeting, translating sentence by sentence as you speak. Nothing to prepare; you start talking immediately; a mistake stops you at that sentence and not before.

Python is the second kind. There is no `make`. You write `hello.py` and run it with `python hello.py`; the program called `python` reads your file line by line and does what each line says. The price is speed: every line is translated every time it runs. The gain is everything else: you try an idea in seconds, you fix and rerun without a build step, and you can type a line and see its result immediately.

> [!code] hello0.c → hello0.py · the whole program
> The C version needs an `#include`, a `main`, braces, a semicolon and a `\n`. The Python version is one line. There is no `main` because the file *is* the program: Python starts at the top and runs down. There is no `#include <stdio.h>` because printing is built in. `print` adds the newline for you.

<Terminal lines={['python hello0.py']} out={`hello, world`} />

Three things to notice before we go on, because they decide how every Python program looks:

- **No semicolons.** A line ends where the line ends.
- **No braces.** A block is marked by **indentation**: four spaces. In C, indentation was for humans and the braces were for the compiler. In Python the indentation *is* the syntax. Get it wrong and the program means something else, or does not run.
- **No type declarations.** `x = 50` creates `x`. Python figures out that it is an int. We will come back to what that really means.

> [!tip] `python` or `python3`?
> On most systems today `python` is Python 3; on some older ones `python` is the long-dead Python 2 and `python3` is the one you want. In the codespace and in Colab both work. If `python --version` prints `3.something`, you are fine.

## Six ways to run Python

In C you had one way to work: a terminal, a compiler, an editor. Python gives you several, and professionals use all of them, for different jobs. Here are the six you should know, each with the exact steps. Try at least three this week.

Type `python` with no file name and you get a prompt, `>>>`. Type an expression, press Enter, see the result. This is the **REPL** (read, evaluate, print, loop), and it is where Python programmers test an idea before they write it into a file.

## Numbers, and the first surprise

> [!code] calculator0.c → calculator0.py → calculator1.py · addition
> The C version declares `int x`, calls `get_int`, prints with `%i`. `calculator0.py` is the same with CS50's `get_int`. `calculator1.py` removes the library: `input` gives a string, `int(...)` converts it, and that is the general pattern, `int(input("x: "))`. > [!code] calculator2.py → calculator3.py · division, and floats
> In C, `1 / 3` was `0`, because int divided by int truncates. In Python, `/` always gives a float: `1 / 3` is `0.3333…`. If you want the C behaviour, integer division, there is a separate operator, `//`. `calculator3.py` prints the result with fifty decimals, `f"{z:.50f}"`, and shows you that the **float imprecision of week 3 is still there**: Python uses the same 64-bit floats as C, because it is C underneath.

Integers, on the other hand, are better than in C. There is no overflow: a Python int grows as large as it needs to.

> [!code] bigint.py · 2 to the power of 200, no problem
> `2 ** 31` is already past a C `int`; `2 ** 200` is fine. Python checks every integer operation and, when the number no longer fits in a machine word, switches to a slower representation that can hold any size. That check is one of the reasons Python arithmetic is slower than C. Floats stay what they were.

### Types, without declarations

In C a variable was a box of a fixed size and type: `int x` was four bytes, forever an int. In Python a variable is a **name tag**. `x = 50` creates the value `50` somewhere in memory and hangs the tag `x` on it. `x = "fifty"` creates a string and moves the tag. The value has a type; the name does not. This is **dynamic typing**.

> [!code] nametags.py · the same name, three types
> `type(x)` tells you what the tag is currently on. Then the lines that matter: `1 + 2` is `3`, `"1" + "2"` is `"12"` (two strings glued), and `"1" + 2` is an error, because Python does not guess. It is dynamic, not sloppy. You convert explicitly, `int("1") + 2`, the way `calculator1.py` did.

<CodeFiles dir="week-08" files={["nametags.py"]} />

> [!warning] Never name a file after a module
> This program was first called `types.py`, and it broke every other program in the folder: `types` is a module of Python's standard library, and `import csv` loads `csv`, which loads `re`, which loads `enum`, which does `from types import …` and found our file instead. The same happens with `random.py`, `string.py`, `copy.py`, `math.py`, `test.py`. If an import fails with a message that makes no sense, look at the names of your own files first.

The built-in types you will use this week, all of them available without an `#include`:

| Type | Example | Notes |
|---|---|---|
| `int` | `50`, `2 ** 200` | no overflow |
| `float` | `3.14`, `1 / 3` | same imprecision as C |
| `str` | `"hello"`, `'hello'` | immutable; no `\0`; dozens of methods |
| `bool` | `True`, `False` | capital letters |
| `list` | `[72, 73, 33]` | an array that grows; any types inside |
| `dict` | `{"Kelly": "+1-617"}` | a hash table: key → value |
| `tuple` | `(3, 4)` | a fixed list; cannot change |
| `set` | `{"cat", "dog"}` | each value once; instant `in` |
| `None` | `None` | "no value"; what `NULL` wanted to be |

## Conditions

The same `if`, `else`, and the operators you know (`==`, `!=`, `<`, `<=`, `and`, `or`, `not`, in words instead of `&&`, `||`, `!`). What changes is the shape: a colon instead of braces, indentation for the body, and `elif` instead of `else if`.

> [!code] compare3.c → compare3.py · if, elif, else
> Line for line the same program. Count the characters: the Python version is about a third of the C. Note `elif`, and that the condition has no parentheses, though it may have them.

<CodeFiles dir="week-08" files={["compare3.py", "compare3.c"]} />

> [!code] agree0.py → agree2.py · or, in, and lower()
> `agree0.py` checks `s == "Y" or s == "y"`. `agree1.py` says the same thing better: `s in ["y", "yes"]`, where `in` asks whether a value is inside a list. `agree2.py` applies `.lower()` to the input first, so `YES` and `Yes` and `yes` all agree. > [!definition] Truthiness
> In an `if`, Python treats `0`, `0.0`, `""`, `[]`, `{}` and `None` as false and everything else as true. So `if name:` means "if the name is not empty", and `while items:` means "while the list has something in it". You will see it everywhere in real code.

## Strings, without the pain

In week 4 a string was an array of chars ending in `\0`; in week 6 it was a pointer; copying one took `malloc`, `strcpy` and `free`. In Python a string is a value. You cannot change it in place, and you never have to free it.

## Lists and dictionaries: week 7, built in

This is where Python pays you back for week 7. A **list** is an array that grows by itself, the `realloc` story handled for you. A **dict** is a hash table: a key, a value, and a lookup that costs about one step. Both are written in C inside the interpreter, by people who did exactly what you did in Lab 6, once, very carefully.

> [!code] scores0.py → scores2.py · a list, its sum and its length
> `scores = [72, 73, 33]` is a list. `sum(scores)` and `len(scores)` are built in; the average is one line. `scores1.py` starts with an empty list `[]` and grows it with `.append(score)`, no capacity, no `realloc`. `scores2.py` grows it with `+=`, which glues lists the way `+` glues strings.

<CodeFiles dir="week-08" files={["scores0.py", "scores1.py", "scores2.py"]} />

> [!code] phonebook0.py → phonebook1.py · linear search, then just `in`
> `phonebook0.py` is week 5's linear search: a `for` over the names with a `break` when found. The strange part is the `else` on the loop: it runs if the loop finished *without* a break, which is exactly "not found". `phonebook1.py` replaces the whole loop with `if name in names`. Same algorithm underneath, O(n), one line.

## Exceptions: what happens when `int("cat")` fails

In C, a function told you about failure by returning a special value: `NULL`, `-1`, `false`, and you had to remember to check. Python raises an **exception**: the program stops at that line with a message, unless you catch it.

> [!code] integer0.py → integer3.py · is it a number?
> `integer0.py` asks the string, `n.isnumeric()`. `integer1.py` just calls `int(...)` and crashes on `cat` with `ValueError`. `integer2.py` wraps the call in `try:` and catches `except ValueError:`, the Python way of saying "attempt this; if that specific thing goes wrong, do this instead". `integer3.py` adds `else:`, the block that runs only if nothing went wrong, keeping the happy path and the sad path visibly apart.

> [!warning] pip installs code written by strangers
> `pip install` downloads a package and runs it on your machine with your permissions. Almost always that is fine, because the packages above are used by millions and watched closely. ## Speller in twenty lines, and the price of comfort

In Lab 6 you wrote `dictionary.c`: a hash table with buckets, nodes, `malloc` for every word, `strcasecmp`, a hash function, and `unload` to free everything. Here is the Python version, by CS50.

> [!code] dictionary.py and speller.py · the whole dictionary is a set
> `words = set()` makes a hash table. `load` opens the file and `words.update(file.read().splitlines())`, one line for the whole dictionary. `check` is `word.lower() in words`. `size` is `len(words)`. `unload` has nothing to do, because Python frees memory itself (it counts how many tags point at each value and throws the value away when the count hits zero; that is the "garbage collection" you may have heard of). `speller.py` is the C `speller.c` translated line by line, for you to compare.

<CodeFiles dir="week-08" files={["dictionary.py", "speller.py"]} />

Run both on the same text and compare the times. Python's `load` is slower than a good C version, and `check` is about as fast, because the set is a C hash table. So which is better? Wrong question. The right one: **what is the cost of a programmer's hour, and what is the cost of a millisecond?** For a spell checker that runs once, the Python version wins by a week of your time. For the spell checker inside a phone keyboard, running on every keystroke on a battery, the C version wins. Professionals know both and pick.

> [!code] timing.py and timing.c · measure, do not guess
> Adding the numbers from 0 to ten million. The Python `for` loop takes about half a second; the same loop in C takes about a hundredth. That is the famous "Python is 50 times slower". Then two more lines: `sum(range(n))` is six times faster than the loop, because the loop now runs inside the interpreter's C code; and NumPy's `arange(n).sum()` is faster still, because NumPy *is* C with a Python steering wheel. The rule of Python performance: **do not loop in Python over millions of things; call the library that loops in C.** Every AI framework is built on that rule.

## C versus Python, on one page

| | C | Python |
|---|---|---|
| Runs by | compiling to machine code | interpreting, line by line |
| Types | declared, fixed | inferred, dynamic |
| Block | `{ }` | indentation |
| Strings | `char *`, `\0`, `strlen`, `strcpy` | a value with fifty methods |
| Arrays | fixed size, `realloc` to grow | `list`, grows by itself |
| Hash table | you write it (Lab 6) | `dict`, `set` |
| Memory | `malloc` / `free`, valgrind | automatic |
| Integers | overflow at 2³¹ | unlimited |
| Floats | imprecise | imprecise (same hardware) |
| Errors | return values you must check | exceptions |
| Libraries | some, installed by hand | half a million, `pip install` |
| Speed | the yardstick | 10–100× slower in loops; C speed through libraries |
| Best for | operating systems, embedded, games, the engine under everything | AI, data, scripts, web backends, prototypes, almost everything else |

The lesson of the semester, in one line: **learn the slow, exact language first, and the fast, comfortable language becomes transparent.** You are now someone who can read a traceback and picture the memory. Most Python programmers cannot.

## Summary

- Python is **interpreted**: no compile step, instant feedback, slower execution. `python file.py` runs a file; `python` alone is the REPL.
- You can run it in the **codespace**, locally with **Miniconda + VS Code** (one environment per project), in **Jupyter**, in **Colab** (nothing to install, free GPU), or in **Python Tutor** to see the memory. Choose by the task.
- The syntax drops semicolons, braces and declarations: blocks are **indented**, `for i in range(n)` is the loop, `def` makes a function, `if __name__ == "__main__": main()` ends the file.
- Built-in types: `int` (no overflow), `float` (same imprecision), `str` (immutable, many methods), `bool`, `list`, `dict`, `tuple`, `set`, `None`. Variables are **name tags** on values.
- `input()` returns a string; convert with `int()` inside `try`/`except ValueError`.
- `list` is a growing array; `dict` and `set` are hash tables: week 7, built in.
- `with open(...) as file:` and the `csv` and `json` modules handle files; `sys.argv` and `sys.exit` handle the command line.
- **Libraries** are the superpower: `pip install`, then `import`. Pillow, requests, matplotlib, NumPy, scikit-learn. Install carefully.
- Python is slow in loops and fast through libraries written in C. That is not a contradiction; it is the design.
