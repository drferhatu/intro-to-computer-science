## Goal

Four short programs, each about one idea from the lecture. In `swap.c` you turn the broken by-value swap into the pointer version with your own hands. In `copy.c` you make a real copy of a string, which means asking for memory and giving it back. In `leaks.c` you meet valgrind, the referee that watches every byte your program touches, and fix three bugs it points at. In `filter.c` you edit a picture: the file reading and writing is done for you, and you write the two functions that change the pixels.

<Step n={2} title="Part A · swap.c (2 points)" time="10 min" id="part-a">

The file contains the lecture's broken `swap0.c`: the function receives copies of `x` and `y`, swaps the copies, and `main` never notices. Turn it into `swap1.c`:

1. The prototype and the definition take pointers: `void swap(int *a, int *b)`.
2. Inside, work through the pointers: `int tmp = *a; *a = *b; *b = tmp;`.
3. In `main`, pass the addresses: `swap(&x, &y);`.

<Step n={3} title="Part B · copy.c (2 points)" time="15 min" id="part-b">

Read a string, make a **real** copy, uppercase the copy, print both, free the copy:

<Terminal lines={['make copy', './copy']} out={`s: hello, world

The lecture's `copy5.c` is the model. `malloc(strlen(s) + 1)` for the characters plus the zero, check for `NULL`, `strcpy(t, s)`, then a loop with `toupper` over `t` only, two `printf`s, and `free(t)`. Run it under the referee before you move on:

<Terminal cmd="valgrind ./copy" out={`s: test
s: test
t: TEST
==1234== HEAP SUMMARY: ... All heap blocks were freed -- no leaks are possible
==1234== ERROR SUMMARY: 0 errors from 0 contexts`} />

The checks run exactly this: the output, and a valgrind report with no errors and no leaks. If you see `definitely lost`, a `free` is missing; if you see `Invalid write`, the copy ran past the memory you asked for (did you forget the `+ 1`?).

</Step>

<Step n={4} title="Part C · leaks.c (2 points)" time="15 min" id="part-c">

This program should read `n`, build the numbers 1 to `n` in an array on the heap, and print their sum. It compiles, and for small `n` it may even print the right answer, but it has three memory bugs. Do not read the code first; run the referee first and let it tell you:

<Terminal lines={['make leaks', 'valgrind ./leaks']} out={`n: 4
==1234== Invalid write of size 4
==1234==    at 0x...: main (leaks.c:26)
...
sum = 10
==1234== HEAP SUMMARY: ... 4 bytes in 1 blocks are definitely lost`} />

Each line of the report names a line of your code. Three questions, one per bug: how many *bytes* does `malloc` need for `n` ints (hint: `sizeof(int)`)? Where does the fill loop stop? What is missing at the end? When valgrind says `0 errors` and `no leaks are possible`, you are done; the checks also read your source for the three fixes.

</Step>

<Step n={5} title="Part D · filter.c (4 points)" time="35 min" id="part-d">

`main` is written for you. It checks the arguments, reads the two BMP headers, loads the pixels into a two-dimensional array `image[height][width]` of `RGBTRIPLE` (three bytes: `rgbtBlue`, `rgbtGreen`, `rgbtRed`), calls your filter, and writes the result with the padding handled. You write two functions:

<Terminal lines={['make filter', './filter grayscale images/smiley.bmp images/out-gray.bmp', './filter reflect images/smiley.bmp images/out-mirror.bmp']} />

**grayscale.** For every pixel, compute the average of its red, green and blue, rounded to the nearest whole number with `round()` from `<math.h>` (divide by `3.0`, not `3`, so that you do not truncate), and store that average in all three channels. Two nested loops, `i` over rows, `j` over columns, and `image[i][j].rgbtRed` to reach a channel.

**reflect.** Mirror each row: swap the first pixel with the last, the second with the second-to-last, and so on up to the middle. You can swap a whole `RGBTRIPLE` at once with a temporary variable, exactly like the ints in Part A. The loop over `j` runs to `width / 2`; going further would swap everything back.

Open your output files in the Codespaces editor (click them in the explorer; VS Code shows images) or read them with the notebook. The checks compare your pixels with the expected ones on `tiny.bmp`, which has padding, and `smiley.bmp`, which does not, so a correct `reflect` has to work for both.

> [!tip] Check with the notebook
> `lab05.ipynb` prints the pixels of `tiny.bmp` and computes grayscale and reflect in Python. If your C output disagrees, you know which function to look at.

</Step>

## Troubleshooting

> [!note] `valgrind: command not found` in the codespace
> The setup did not finish; run `bash .devcontainer/setup.sh` once.

> [!note] Segmentation fault in `copy` or `leaks`
> You wrote to memory you did not allocate, or through a `NULL` pointer. Run the program under `valgrind`; it names the line.

> [!note] grayscale is off by one on some pixels
> You truncated instead of rounding, or divided by the integer `3`. Use `round((r + g + b) / 3.0)`.

> [!note] reflect works on `smiley.bmp` but not on `tiny.bmp`
> Your filter is fine; something touched the padding. Make sure you only change `image[i][j]` and did not edit `main`.
