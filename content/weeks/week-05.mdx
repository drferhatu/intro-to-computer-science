## Same problem, different speeds

Every program you have written so far was judged on one question: does it work? From this week there is a second question that matters just as much in the real world: how **fast** does it work, and how does that change when the input grows? Two correct programs can differ by a factor of a million on the same laptop. This week gives you a way to see that difference before you run anything.

The programs on this page are from CS50's Week 3 lecture, plus a few written for this course where CS50 shows only pseudocode (binary search and the three sorts in C). Each orange box is a program we open in VS Code; the full, copyable source follows each box.

## Linear search

Remember the lockers from the lecture: an array of seven numbers behind seven closed doors. The computer cannot see all of them at once the way you can; it opens one door at a time. The simplest strategy is to start at the left and open doors until you find what you are looking for or run out of doors.

```text
For i from 0 to n-1
    If 50 is behind doors[i]
        Return true
Return false
```

Notice where the `Return false` sits: *after* the loop, not inside an `else`. If you put it inside the loop, the program gives up after the very first door that is not 50. This is the most common mistake in the first search students write, and the pseudocode makes it visible before any C is typed.

> [!code] search0.c → search1.c · linear search for numbers, then for strings
> [search0.c](/c/week-05/search0.c) is the pseudocode in C: a loop over the array, an `if` with `==`, `return 0` when found and `return 1` after the loop when not. [search1.c](/c/week-05/search1.c) searches an array of strings and runs into something important: you cannot compare two strings with `==`. That operator would compare where the strings live in memory, not what they say (week 6 explains why). The right tool is `strcmp` from `<string.h>`, which returns 0 when two strings are identical. Every time you see `if (strcmp(a, b) == 0)`, read it as "if a and b are the same text".

## Binary search

If the doors are **sorted**, you can do much better. Open the middle door. If the number you want is smaller, everything to the right is useless; if larger, everything to the left is. Either way you have thrown away half the problem with one comparison.

```text
If no doors left
    Return false
If 50 is behind doors[middle]
    Return true
Else if 50 < doors[middle]
    Search doors[0] through doors[middle - 1]
Else if 50 > doors[middle]
    Search doors[middle + 1] through doors[n - 1]
```

> [!code] binary.c · halving, step by step
> [binary.c](/c/week-05/binary.c) keeps two indices, `low` and `high`, and moves one of them after every comparison. It prints which index it looks at, so you can watch the range shrink: in an array of seven, at most three doors are opened. In an array of a billion, at most thirty-one. The price is that the array must be sorted first, which is why the rest of this week is about sorting.

## Running time

We need a way to talk about speed that does not depend on whose laptop is faster. Computer scientists count **steps** as a function of the input size *n* and keep only the shape of the curve, not the constants. That notation is **Big O**, and it describes the upper bound, the worst case.

| Big O | Name | Example this week | Steps for n = 1 000 000 |
|---|---|---|---|
| O(1) | constant | reading `numbers[3]` | 1 |
| O(log n) | logarithmic | binary search | 20 |
| O(n) | linear | linear search | 1 000 000 |
| O(n log n) | linearithmic | merge sort | 20 000 000 |
| O(n²) | quadratic | selection sort, bubble sort | 1 000 000 000 000 |

Three symbols, one idea each. **O** is the worst case: linear search is O(n) because the number might be behind the last door. **Ω** (omega) is the best case: linear search is Ω(1) because the number might be behind the first door. When the best and worst case have the same shape, we write **Θ** (theta): selection sort is Θ(n²), it does the same work whether the list is already sorted or not.

Why do constants not matter? Because for large n they are drowned out. An algorithm that takes 3n steps and one that takes n steps are both O(n); an algorithm that takes n²/100 steps still loses to one that takes 1000·n steps once n passes 100 000. Big O is a statement about *scaling*, and scaling is what decides whether a program survives contact with real data.

## Sorting

Sorting is the price of binary search, and it turns out to be one of the richest problems in computer science. Three algorithms, from the most obvious to the one that actually gets used.

### Selection sort

Look through the whole list for the smallest number and swap it to the front. Then look through what is left for the next smallest, and so on. On the first pass you look at n numbers, on the second n − 1, then n − 2, down to 1. That sum is n(n − 1)/2, and the shape of that is n²: selection sort is Θ(n²).

> [!code] selection.c · the list after every pass
> [selection.c](/c/week-05/selection.c) sorts eight numbers and prints the array after each swap, so you can see the sorted part growing from the left. Notice that the inner loop always runs to the end of the array, however the data looks; that is why the best case is no better than the worst.

<CodeFiles dir="week-05" files={["selection.c"]} />

### Bubble sort

Walk along the list comparing each pair of neighbors and swap them if they are in the wrong order. After one pass the largest number has bubbled to the end; after two passes the two largest are in place. In the worst case that is also n² steps, but bubble sort has one trick selection sort lacks: if a whole pass makes no swap, the list is sorted and you can stop. On an already sorted list bubble sort finishes in one pass, so it is O(n²) but Ω(n).

> [!code] bubble.c · stop when nothing moves
> [bubble.c](/c/week-05/bubble.c) prints the array after each pass and uses a `bool swapped` flag to stop early. Feed it a sorted array in your head and count the passes.

<CodeFiles dir="week-05" files={["bubble.c"]} />

### Merge sort

Both sorts so far are quadratic. Doubling the input quadruples the time; a million numbers take a trillion steps. Merge sort breaks the pattern with one idea: sorting a list is easy if you already have two sorted halves, because merging two sorted lists is a single pass. So sort the left half, sort the right half, merge. How do you sort the halves? The same way. The recursion stops at lists of one element, which are sorted by definition.

```text
If only one number
    Quit
Else
    Sort left half of numbers
    Sort right half of numbers
    Merge sorted halves
```

Each level of halving costs n steps to merge, and there are log₂ n levels, so merge sort is Θ(n log n). For a million numbers that is twenty million steps instead of a trillion: the difference between a blink and twelve days. The cost is memory: merging needs a second array to merge into.

> [!code] merge.c · watch the halves come back together
> [merge.c](/c/week-05/merge.c) prints every merged range, indented by its depth in the recursion, so the structure of the algorithm is visible in the output: the single elements merge into pairs, the pairs into fours, the fours into the final sorted list.

## Recursion

Merge sort was defined in terms of itself, and that deserves a closer look. A function that calls itself is **recursive**. It sounds circular, and it would be, except that every recursive function has a **base case**, an input so small that the answer is known without any further calls. Everything else is reduced one step towards that base case.

> [!code] iteration.c → recursion.c · the same pyramid, two ways
> [iteration.c](/c/week-05/iteration.c) draws a left-aligned pyramid with two nested loops, as you did in Lab 2. [recursion.c](/c/week-05/recursion.c) says something different: a pyramid of height n is a pyramid of height n − 1 followed by one more row of n hashes. The function `draw(n)` calls `draw(n - 1)` first, then prints its own row. The base case is `if (n <= 0) return;`. Without that line the function would call itself forever, the call stack would overflow, and the program would crash. Trace `draw(3)` by hand: it calls `draw(2)`, which calls `draw(1)`, which calls `draw(0)`, which returns; then the rows are printed on the way back up, 1, 2, 3 hashes.

<CodeFiles dir="week-05" files={["iteration.c", "recursion.c"]} />

Recursion is not a trick for pyramids. It is the natural way to express anything that is defined in terms of a smaller version of itself: file systems inside folders inside folders, the structure of a sentence, a chess game, and, in two weeks, the data structures that make databases fast.

## Summary

- Linear search looks at every element: O(n). Binary search halves the range each step: O(log n), but the array must be sorted.
- Big O describes how steps grow with n, ignoring constants. O is the worst case, Ω the best, Θ when they match.
- `strcmp(a, b) == 0` is how you ask whether two strings are the same text; `==` compares something else.
- A `struct` bundles related data into a type of your own; `.` reaches inside it.
- Selection sort and bubble sort are Θ(n²) and O(n²) respectively; bubble sort can stop early. Merge sort is Θ(n log n) and uses recursion.
- A recursive function calls itself on a smaller input and stops at a base case.
